# Contributing to fqdn-network-policy

Thanks for taking a look. This project is a small, focused Kubernetes controller — most
contributions are welcome, but please open an issue first for anything beyond a small fix so we
can agree on the approach before you put time into it.

By participating, you're expected to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Before you start

- **Small fix (typo, obvious bug, doc correction)?** Just open a PR.
- **New feature, behavior change, or anything touching a CRD type?** Open an issue describing the
  problem and proposed change first. Take a look at how recent issues are scoped (a clear
  Problem / Proposed change / Acceptance criteria / Out of scope shape) — it makes review much
  faster on both sides.
- **Security issue?** Don't open a public issue — see [SECURITY.md](SECURITY.md).

## Development setup

Requires Go 1.26+, `make`, and Docker (for the demo and image builds). `kind`, `kubectl`, and
`jq` are needed to run `./demo.sh`.

```bash
git clone https://github.com/kunaldevxxx/fqdn-network-policy.git
cd fqdn-network-policy
go build ./...
```

Common tasks (see `make help` for the full list):

```bash
make generate        # regenerate zz_generated.deepcopy.go after type changes
make manifests        # regenerate config/crd/bases/*.yaml and config/rbac/role.yaml
make build             # compile ./bin/manager
make kubectl-plugin    # build the kubectl-fqdn_policy plugin to bin/
make run               # run the controller against your current kubeconfig context
make fmt vet           # gofmt + go vet

go test -short ./...             # unit tests (skips network-dependent tests)
go test -short -race ./...       # same, with the race detector (what CI runs)
go test ./...                    # full suite, including tests that hit real DNS
```

`./demo.sh` spins up a real `kind` cluster with Calico, deploys the controller, and proves
FQDN-based egress control end to end — it's the fastest way to see a change actually working
against a live cluster rather than just passing tests.

## Making a change

1. **CRD type changes** (`api/v1alpha1/*_types.go`): after editing, run `make generate` (deepcopy)
   and `make manifests` (CRD YAML + RBAC), and commit the regenerated output alongside your
   change. **Never hand-edit `zz_generated.deepcopy.go` or anything under `config/crd/bases/`** —
   both get silently overwritten and a hand-edit there will look like it worked until the next
   `make generate` reverts it.
2. **New RBAC needs**: add a `+kubebuilder:rbac` marker on the relevant reconciler (see the
   existing markers in `internal/controller/*.go`) rather than hand-editing `config/rbac/role.yaml`
   — that file is also generated by `make manifests`.
3. **Tests**: this repo uses plain `testing.T` + `testify` (`assert`/`require`), not
   ginkgo/gomega/envtest. Controller tests use `sigs.k8s.io/controller-runtime/pkg/client/fake`
   and call `Reconcile` directly — see `internal/controller/fqdnnetworkpolicy_controller_test.go`
   for the pattern (stub resolver, fake client, assert on the object read back). Network-dependent
   DNS tests should guard with `if testing.Short() { t.Skip(...) }`.
   CI enforces a 60% minimum coverage floor on `internal/dns`, `internal/netpol`, and
   `internal/webhook` — new code in those packages needs tests to land.
4. **New Prometheus metrics**: add them under a matching (or new) category block in
   `internal/metrics/metrics.go` and don't forget the `metrics.Registry.MustRegister(...)` call —
   it's easy to add the `var` and forget the registration.
5. **CHANGELOG.md**: add an entry under the top `Unreleased` section (create one if the last
   entry is already a tagged release) describing what changed and why, in the same
   problem/solution style as existing entries.

## Pull requests

- Keep PRs focused — one feature or fix per PR is much easier to review than a bundle.
- Fill out the PR template; the checklist mirrors the steps above.
- CI runs lint (`golangci-lint`), unit tests with coverage gating, a build of both binaries, a
  full KinD+Calico e2e run, and a Helm chart lint. All of it needs to pass before merge.
- Squash-merge is fine; write a commit message that explains *why*, not just *what*.

## Reporting bugs / requesting features

Use the issue templates — they ask for the details that are actually needed to act on a report
(controller version, Kubernetes version, resolver mode, CNI, relevant YAML) so we're not stuck
going back and forth for basics.
